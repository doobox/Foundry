Template API

Put values where they belong

Foundry processes the HTML, CSS, JavaScript, PHP and editor CSS named by Info.plist. The developer owns the resulting structure and selectors; scope controls how often each template is emitted.

Partly proposed. Scoped CSS, JavaScript, PHP export, local PHP preview and page-scoped HTML placement are implemented. Sass/SCSS compilation remains proposed.

Template scope

Declare each additional CSS template as a dictionary containing its path and optional scope. Scope is about lifetime and deduplication, not selector choice.

instance
Default. Processed once for every component instance. Instance identity and control macros are available.
page
Processed once on each editing page that uses the component, regardless of how many instances are present. Deduplicated in the shared production stylesheet.
site
Processed once in the canvas preview and once in the shared production stylesheet when the component is used anywhere.
<key>files</key>
<array>
    <dict>
        <key>path</key><string>component.css</string>
        <key>scope</key><string>instance</string>
    </dict>
    <dict>
        <key>path</key><string>shared.css</string>
        <key>scope</key><string>page</string>
    </dict>
    <dict>
        <key>path</key><string>site.css</string>
        <key>scope</key><string>site</string>
    </dict>
</array>

Page and site templates are deduplicated by component bundle identifier. They reject {{ id }}, {{ component.attributes }}, {{ control.* }}, editable text, conditions and slots because there is no single component instance to supply those values.

HTML placement

Additional HTML templates use page scope and require placement: headStart, headEnd, bodyStart or bodyEnd. Foundry emits each template once on a page when its component package is used.

<dict>
    <key>path</key><string>metadata.html</string>
    <key>scope</key><string>page</string>
    <key>placement</key><string>headEnd</string>
</dict>
Placement is separate from scope. Scope answers “how often?” while placement answers “where?”. The primary html template remains instance-scoped in the normal component flow. Additional placed HTML deliberately uses page scope; site-scoped HTML is not accepted because an exported site has no single HTML document.

JavaScript

JavaScript templates accept instance, page and site scope. Foundry processes their allowed macros and emits the resulting source in a script block at the end of the body. The code runs as ordinary website JavaScript under the browser’s normal security rules.

Each JavaScript file is wrapped in its own immediately invoked function by default, keeping its variables out of the global scope. The developer writes an ordinary file; Foundry places the complete processed source inside the wrapper.

<dict>
    <key>path</key><string>component.js</string>
    <key>scope</key><string>instance</string>
    <key>closure</key><true/>
</dict>

The component helper

An instance-scoped closure receives component, the native HTML element carrying that instance’s data-foundry-id from {{ component.attributes }}. The developer can place {{ id }} wherever their markup and styling require; Foundry does not use it to locate the component.

<div id="{{ id }}" {{ component.attributes }}>
    <button class="show-button">Show message</button>
    <p class="message" hidden>Hello from Foundry</p>
</div>
const button = component.querySelector(".show-button");
const message = component.querySelector(".message");

button.addEventListener("click", () => {
    message.hidden = false;
});

Foundry produces:

(function (component) {
    "use strict";

    const button = component.querySelector(".show-button");
    const message = component.querySelector(".message");
    button.addEventListener("click", () => { message.hidden = false; });
})(document.getElementById("foundry-a12b"));

Page- and site-scoped closures receive page, which is the browser’s document. closure is optional and defaults to true. Set it to false only when the file intentionally creates globals; raw files receive no helper. Each template receives a separate closure.

Instance identity

{{ id }}

Resolves to a stable, CSS-safe ID unique to the instance, such as foundry-a12b….

<article id="{{ id }}" {{ component.attributes }}>…</article>

#{{ id }} { border-radius: 12px; }
#{{ id }} .title { font-weight: 700; }

Control values

{{ control.<id> }}

Resolves a value declared by customItems or a named theme control. Responsive values resolve at the breakpoint currently being rendered.

#{{ id }} {
    max-width: {{ control.maxWidth }}px;
    text-align: {{ control.alignment }};
}

#{{ id }} .media {
    opacity: {{ control.imageOpacity }};
}

{{ control.<id>[<index>] }}

Resolves one member of a control array using a zero-based index. The equivalent property spelling is also accepted.

#{{ id }} {
    --primary: {{ control.palette[0] }};
    --secondary: {{ property.palette[1] }};
    padding: {{ control.insets[0] }}px {{ control.insets[1] }}px;
}

The index must refer to an item declared by the control’s count. See Control arrays.

Component hooks

{{ component.attributes }}
Required editor metadata. Place it on the element that represents the component.
{{ component.class }}
Foundry’s generated class fragment when a template needs to append it to its own class attribute.
No hidden selector rules. Foundry does not assume that a control belongs on the top-level element. Use the same control more than once or target any descendant your component requires.

Supported template files

HTML
Primary instance markup and additional page-scoped head/body markup.
CSS
Component styles used by the canvas and export.
JavaScript
Client-side component behaviour with scope-appropriate values substituted.
Sass and SCSS Proposed
Developer-authored stylesheet source with macros substituted and compiled to CSS.
PHP
Publish-only server-side source with scope-appropriate macros substituted and placed before the exported page doctype.
Editor CSS
Canvas-only CSS excluded from production export.
PHP export and preview are implemented. Set <key>requiresPhp</key><true/> and declare .php files under templates.files. Instance PHP is emitted for every component; page and site PHP is emitted once per package on each page. Foundry executes the generated page with its bundled PHP runtime in local preview, including query strings, request bodies, response status and headers. Development errors are shown in preview and do not change production export.

Editor CSS

Editor CSS adds authoring affordances that are useful inside Foundry but should not appear on the published site. A component might use it to:

  • give an empty container enough height to receive a dropped component;
  • outline or tint an editable region;
  • show a short placeholder label when real content is absent;
  • make a small interaction target easier to select on the canvas.

Name the file with editorCSS in Info.plist:

<key>templates</key>
<dict>
    <key>html</key><string>component.html</string>
    <key>files</key><array>
        <dict><key>path</key><string>component.css</string></dict>
    </array>
    <key>editorCSS</key><string>editor.css</string>
</dict>

editor.css is processed with the same instance and control macros as every other template:

#{{ id }} .content {
    min-height: 72px;
    outline: 1px dashed rgb(0 0 0 / 0.25);
    outline-offset: -1px;
}

#{{ id }} .content:empty::before {
    content: "Drop components here";
    color: rgb(0 0 0 / 0.45);
}

Foundry loads this stylesheet for the editing canvas and excludes it from production export.

Keep it editorial. The normal component CSS should remain the source of truth for the published layout. Editor CSS should improve selection, empty states and drop targets without disguising how the component will actually render.
Proposed stylesheet processing. Sass and SCSS compilation remains planned. PHP preview execution and authored JavaScript are implemented.

The currently implemented html, files and editorCSS entries are declared under templates in Info.plist.
